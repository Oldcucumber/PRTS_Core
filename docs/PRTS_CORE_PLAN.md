# PRTS Core 执行计划与当前状态

记录日期：2026-09-21；更新日期：2026-09-22。状态：**已实现离线 Python Demo，导航、障碍影响路径、真实语音问询与持续等待已做回放。** 本文是原始计划，后部暂停记录保留为历史；已交付范围见 [运行说明](../PRTS_CORE_README.md)，实际结果与未完成项见 [验证记录](PRTS_CORE_RESULTS.md)，不能将计划条目当作实现证明。

这份计划以最新范围为准：PRTS 是产品，PRTS Core 是后端核心。先在 Python 上验证真实感知、理解与音视频任务机制，效果稳定之后再做速度、量化和 Apple 迁移。约每秒 2 帧只是用户可接受的参考，不是目标、KPI 或验收门槛。下面的入口、数据量和验收要求都是拟实施内容，不能当成已经交付的功能。

1. **推荐路线与首轮边界**

   推荐 MiniCPM-V 4.6 + 独立离线中文 ASR + 中文 OCR + 简单任务状态；现有地面分割/局部候选通道与新增目标检测作为小脑。先使用能取得较好效果的精度、图像细节和上下文，不因手机资源假设提前压缩输入。模型只负责它适合的识别与理解，等待目标、取消、去重和证据时间由 Python 维护。

   2026-09-22 用户补充：模型不限定 MiniCPM-O；V 系列只是体量上的优先候选，可替换其他本地 ASR、视觉或流式模型，也可通过最新帧、短期记忆、事件触发与任务状态构建系统层持续交互。当前实现保留模块边界，先以同一输入上的实际效果决定替换，不把连续轮询称为原生全双工。

   即时询问和持续等待共用一条感知管线，不按四段视频分别造功能。不建设前端、页面、服务部署、多用户系统或复杂异常框架。第一轮必须有真实模型输入输出、离线回放、可检查事件与失败案例；不以空接口或模拟输出充当成果。

   V 4.6 官方资料将其描述为约 1.3B 的图像/视频理解模型；其视觉压缩可选 4x/16x。O 4.5 约 9B，具备原生音视频全双工能力。这里优先 V，是根据这两类任务可以由视觉理解、ASR 和任务观察器组合完成作出的工程判断，仍需实验验证。[V 模型卡](https://huggingface.co/openbmb/MiniCPM-V-4.6)、[官方 V/O 仓库](https://github.com/OpenBMB/MiniCPM-V)

   严格区分：文本逐字输出是增量解码；连续取帧是输入调度；ASR/TTS 是独立语音管线；按时间组织多帧和转写才涉及本项目的时序推理；同时采集、播音和允许取消，不等于 O 的原生全双工联合建模。第一轮不因需要“主动提醒”就直接换 O，主动提醒首先是等待任务的触发机制。

2. **输入、任务与输出约定**

   输入支持本地视频及其音轨、图像、WAV，后续在同一入口接摄像头/麦克风；命令可以先由命令行或 JSONL 给出，再接本地 ASR 的用户话语。输入保留媒体时间戳和到达时间，回放时间与实际运行耗时分别记录。用户命令与环境广播是不同输入角色：早期通过调用参数明确角色，不假装已解决同一麦克风里的唤醒、说话人分离或回声消除。

   后端只需要四类动作：`ask`、`wait_start`、`wait_update`、`wait_cancel`。首轮同时维护一个等待任务和一个即时询问；询问结束后继续等待。修改目标产生新的任务版本，旧推理结果不能触发新目标；取消后不再发到达提醒。无需通用工作流引擎。

   输出为 JSONL 事件和中文文本，至少含 `task_id`、`task_version`、事件类型、观察时间范围、发出时间、答案/提醒与证据引用。事件例如 `answer`、`wait_started`、`target_observed`、`need_better_view`、`wait_cancelled`。证据可以是本地帧索引、OCR 字框及文本、ASR 原文和时间段。先保留模型原始结果与最终事件，便于判断错误来自识别还是任务逻辑。模型自述“有信心”不能直接用作校准概率。

   可选输出本地合成音频文件，用于核对播报内容及打断；默认成果以核心事件与文本为准，不依赖音频播放界面。输出语音的开始、取消、完成可以作为后端事件测试。

3. **即时询问：先回答问题，再补场景**

   例子是“这条路叫什么”“门口公告写了什么”“画面里哪一辆是我要的车”。V 读取当前画面和具体问题，中文 OCR 提供可追溯文字；远处小字先定位、保留全图语境再放大局部，必要时结合邻近清晰帧。不可只返回泛泛的场景描述，也不把不清楚的字补成合理地名。

   首轮对照三个配置：V 单独；OCR 单独；V + OCR + 适量邻近帧。V 的图像细节档和切片数量按效果比较，不预先锁死到最低成本。每次输出记录使用了哪一帧，镜头已经转走时说明观察时刻或重新读取，不把旧画面描述成现在。

   建立约 30–50 个有人工核对答案的小样本问题，覆盖道路名牌、公告、交通目标、无法读清和问题指代。这个数量是初始实验规模，可按实际素材调整。四段视频中的题目归入此集合，并保留完整片段用于上下文回放。

   成功标准：文字关键实体按原文核对；问题相关性由逐条审阅判定；无法回答样本应说明具体缺失信息。报告实体完全匹配率、文字字符错误率、问答正确/部分正确/错误/无法核对的数量，以及首次输出和完整答案耗时。首轮可运行基线不要求承诺达到任意百分比；只有真实计数和失败案例齐全，才允许宣称该轮完成。改进版本必须在同一保留集上优于基线，且不能靠把所有问题拒答提高表面正确率。

4. **持续等待：指定目标，观察条件，提醒一次**

   等待任务首先把自然语言转为明确目标：如公交线路、地铁线路及方向、叫号前缀/号码/窗口。保存原话和归一化目标。号码和方向不能丢失；“108 路车”不能仅因检测到任意公交就满足条件。

   视觉支路使用检测定位车辆/屏幕/文字区域，OCR 识别线路、方向、号码和窗口，V 处理语义与指代。目标只露出一瞬间、部分遮挡、相似号码、反方向列车都作为负例。可用短时图像历史帮助确认，禁止无限积累帧。

   叫号音频支路持续保存有限时长音频缓冲，使用 VAD 和有重叠的识别窗口，避免切断“一百零八”或字母前缀。首轮用 Whisper small 本地基线；中文广播号码错得较多时，再在同一片段比较更大 Whisper 或中文专用 ASR。比较后才选择模型，不能把英语/通用榜单当作中文叫号质量证据。[whisper.cpp 的 Apple/C++ 路线](https://github.com/ggml-org/whisper.cpp)、[FunASR 备选工具链](https://github.com/modelscope/FunASR)

   视觉叫号屏与广播分别能提供证据：任一渠道足够明确时可以报告“广播叫到了…”或“屏幕显示…”，不强制二者都出现；二者冲突时保留冲突，继续观察，不能拼接成更肯定的号码。音频转写里的“幺/一”、数字读法、英文字母等通过可审阅的号码解析处理，不无限模糊匹配。

   采用最简单的 `active → matched → notified / cancelled` 状态。提示去重按目标和事件证据进行，重复广播、同一屏幕持续显示不能不断提醒；用户修改目标后重新观察。等待期间即时提问不删除任务，ASR 环境支路保持采集。视觉推理来不及时读取最新可用帧，音频不能照搬“只保留最新一帧”的丢弃策略。

   初始测试约 20–30 条短序列，包含目标出现/未出现、先出现近似号码、重复广播、无声屏幕、黑屏广播、视听冲突、任务修改/取消、等待中提问。合成材料与真实录制分别统计。每条人工标出“证据首次足够明确”的时刻，计算命中数、漏报数、误提醒数、重复提醒数和提醒延迟。相邻片段不得跨入训练集和保留评估集。

   成功标准：小型确定性机制测试中，取消后提醒和同一目标无理由重复提醒均为 0；真实感知测试逐条给出命中/误报/漏报及证据，不以这些机制测试代表识别准确率。合理延迟由短暂可见目标、语句结束与播报体验决定，不能用“达到 2 FPS”代替。

5. **小脑与局部引导保留为独立实验支路**

   保留现有 floor_nav.py 和浏览器原型的运行方式，新后端通过适配使用感知结果，不重写前端。先补真实目标检测和适合户外的语义类别：车行道、行人区域、地面、障碍要明确区分。现有 ADE20K floor 不能直接代表室外人行道，Cityscapes 类预训练模型可作为迁移基线，其汽车视角域差异必须在步行数据上验证。

   用目标框、分割和必要的几何/相对深度过滤当前帧候选区域；跨帧只保存目标与状态证据，不将旧路径平均到新障碍上。近端遮挡、低置信、明显镜头变化和结果过期足以影响结论，保留这些基本处理即可。相对深度不能给出米数，图像通道宽度不能冒充人体净空。

   交通灯颜色识别与“能否过街”分开评估；绿色信号不是安全过街的算法假设。台阶、路沿、坑洞/跌落是明确的能力缺口，优先找有对应标签的样本验证，不能因预训练检测器未报出就认为不存在。全局目的地路线查询与地图包不纳入本轮两类交互交付，后续可作为独立后端能力。

7. **按顺序执行，每一步留下能运行和审阅的东西**

   | 阶段 | 工作 | 可检查产物与进入下一步的条件 |
   |---|---|---|
   | A：事实与基线 | 校验现有工程；本地解码四段视频、ASR 转写、人工抽查问题/应答/关键事件；标明录屏按钮和黑边的处理；建立小样本清单 | 带时间的基线记录、数据清单、题目及事件真值；不能先凭画面假设原系统说了什么或能否打断 |
   | B：真实单次问答 | 下载固定版本 V/OCR/ASR 权重，关闭运行期联网；用本地图片/音视频问句走通问答；先比较 V 与 OCR 配合的实际效果 | 一个 Python 命令得到真实中文答案、证据和耗时；保存原始模型输出与失败样本；排除后台下载/远程 API |
   | C：等待闭环 | 在同一后端接等待、修改、取消、并行询问；车辆/线路识别与叫号视听识别共用目标机制；补合成机制回归和真实素材 | 从音视频输入到一次正确目标提醒的 JSONL；近似号码、取消、重复、视听冲突有逐条结果 |
   | D：小脑与数据对照 | 接真实 YOLO/SEG；在步行片段检查小目标、道路/人行区混淆和障碍；必要时保留深度过滤比较 | 同帧预测/叠加图与独立状态事件；给出模型单独、组合、时序前后的对照，不能靠展示绿色面积证明效果 |
   | E：效果驱动的修正 | 按失败最多的原因调整图像细节、OCR、ASR、取帧/音频窗口；有足够合法标注再小规模微调 | 同一保留集上的前后指标；训练来源与拆分可查；没有数据则不硬做训练 |
   | F：Apple 准备与资源优化 | 冻结较好效果配置后测组件耗时、内存和连续运行；探索转换/量化，列出质量代价和真机验证方法 | 可复现基线、组件预算、转换脚本/接口约定和迁移记录；Windows 未编译的 Apple 项目明确标未验证 |

   执行过程中先保证 A–C 能独立形成有用成果，再推进 D–F。阶段 E 不无限调参：围绕可复现的失败修正，保留修改前基线；当继续改进依赖新真实素材或 Apple 真机时，交付已有成果和准确缺口。上述顺序是一次 goal 的工作路线，不是定时任务，也不表示已经开始通宵执行。

8. **对照与验收方法**

   固定少量开发样本和独立保留样本。先做 `V`、`OCR/ASR`、`V+专用感知`、`再加入短时证据` 的消融。叫号对比仅音频、仅视觉、二者结合，分别报告清晰/噪声/遮挡与真实/合成结果。需要升级 ASR、V 的输入细节或换 O 时，使用同一批失败样本，不能更换测试集后宣布胜出。

   延迟拆开统计输入采集、VAD/ASR、OCR/检测/分割、V 首字与全文、事件生成、可选 TTS；回放速度、视频采样率和真实推理吞吐不能混用。小样本给原始计数、逐条记录和 P50/P95 耗时，不夸大为泛化精度。连续运行测量在效果版本冻结后进行，记录峰值内存、温度/降频和错误，而不是先写大量与模型效果无关的测试。

   只保留有意义的程序检查：号码解析、任务修改/取消、提示去重、过期结果不触发新任务，以及同帧映射/预处理一致性。已有原型的相关检查继续运行。正式结果必须注明哪些在这台 Windows 桌面测得、哪些仅为迁移目标。

9. **V 不够时的 O 回退条件与 Apple 方向**

   若 V 加 ASR/OCR 在字幕文本、跨帧目标或中文广播上失败，先定位是否为分辨率、ASR 错字、任务状态错误；这些问题不能仅靠更换 O 解决。只有任务确实依赖音视频联合时序、声音语义、重叠发言或自然全双工，而且 O 在同一素材上有明确优势时，才把 O 提升为主候选。

   O 评估按组件拆分：语言主干 Q4/Q5/Q8，视觉编码器和投影优先 FP16/INT8，音频编码器分别对中文数字辨识评估，语音生成/声码器独立保留或卸载；若只需听懂和发事件，不默认常驻语音生成。记录每种组合的准确率、峰值和延迟。不能将“9B × 4bit”当作整个运行内存，也不承诺所有量化组合已被当前运行库支持。

   官方 llama.cpp-omni 的 Mac 全双工示例当前列 M4 Max、至少 24GB RAM；这是现有实现要求，不是优化后的理论下界，更不能直接推出 12GB iPhone 已能完成相同体验。[官方部署要求](https://github.com/OpenBMB/MiniCPM-V#minicpm-o-45)

   iPhone 18 Pro 和 Pro Max：本次核查的 iFixit 设备资料均列 **12GB RAM**；没有在本机提取原始 Xcode 设备元数据，因此不声称亲自复核了该文件。[18 Pro](https://www.ifixit.com/Device/iPhone_18_Pro)、[18 Pro Max](https://www.ifixit.com/Device/iPhone_18_Pro_Max)。硬件 RAM、App 动态可用额度、权重文件大小和包含激活/缓存/音视频缓冲的峰值是四个不同量。

   迁移候选为：模型采用 llama.cpp/Metal、Core ML 或 ONNX 对应后端；Python 负责研究、数据和导出，稳定后的几何/时间逻辑可用 C/C++，Swift 只桥接 Apple 输入输出与系统资源。官方 V Apps 有 iOS 工程，可作为具体依赖参考，不把它当成 O 全双工已在 iPhone 可用的证据。[官方 Apps](https://github.com/OpenBMB/MiniCPM-V-Apps)

   组件预算在冻结模型后形成：逐项登记实际权重字节、语言 KV/状态缓存、视觉激活、ASR、OCR/YOLO/SEG、深度、音视频缓冲、TTS 和运行库峰值；比较常驻与按需加载。原始权重近似为参数量 × 每参数字节，但量化比例、额外尺度与运行峰值必须实测，不用此公式承诺能装进手机。iOS 通过 `os_proc_available_memory`、进程 footprint、`thermalState` 与 Instruments 长时间记录获得预算，初始不设虚假的“12GB 都可分配”前提。[Apple 内存接口](https://developer.apple.com/documentation/os/os_proc_available_memory)、[Apple 温度状态](https://developer.apple.com/documentation/foundation/processinfo/thermalstate-swift.property)

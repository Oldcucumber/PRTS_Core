# 公交判断为何需要 29 秒

2026-09-22，真实 Citybus 20 视频，Qwen3-VL-4B Q4_K_M + Q8 视觉，官方 llama.cpp b10964，6 个 CPU 线程。帧采集到判断产生为 29.203 秒；模型调用自身 27.741 秒；TTS 在结果之后另用 0.032 秒。

| 环节 | 耗时 | 依据 |
|---|---:|---|
| 图片编码 | 8.816 秒 | native-stderr.log 的 image slice encoded |
| 480 个图像 token 输入语言模型 | 10.820 秒 | image decoded batch 日志；这是图像提示预填充，不是答案生成 |
| 模型调用其余部分 | 约 8.105 秒 | 总调用耗时减前两项，含文字提示、生成及内部开销，尚未进一步单独计时 |
| 模型调用之外 | 约 1.462 秒 | 画面年龄减模型调用耗时，含前置处理与调度，尚未进一步单独计时 |

原始日志在 ZIP 的 `outputs/stage2/streaming/citybus20-brain-v2/`。随 Git 保存精简数据见 `validation/20260922/latency.json`。

## 已查明的实现原因

`prts_core/native_vlm.py` 的 `use_gpu` 默认 false，`local_backend.py` 未覆盖这个值。C++ 设置 `n_gpu_layers=0` 且视觉 `use_gpu=false`；原始日志确认视觉走 CPU。小脑的 DirectML 加速不等于大脑也使用 GPU。

该构建未启用 CUDA/Vulkan/BLAS，关闭了额外 CPU 权重重排副本以减少内存占用。每次请求清空语言模型 KV，上下文和新图像重新处理；没有连续视觉缓存。虽然 C ABI 支持片段输出，等待任务仍在完整 JSON 解码后判断是否提醒。不存在配置成等待 29 秒的定时器，也不是 TTS 导致延迟。

## 下一步应验证

1. 先增加分阶段计时：视觉编码、文字/视觉预填充、首个输出、完整决策及证据年龄，保留端到端测量。
2. 比较不依赖 CUDA 的硬件加速路径；Windows 可探索 Vulkan，Apple 验证 Metal，不能提前宣称已经支持或达到某一延迟。
3. 缩短决策输出，评估视觉分辨率与目标区域；裁剪仍需保留车辆实体和标牌关系，避免把站牌误判为到车。
4. 评估受控缓存和最新帧调度。取消、改目标、相机移动必须使相关缓存失效，不能依赖旧画面完成当前等待。
5. 对 MiniCPM 做模型专用端侧配置与提示词比较。当前 CPU/GGUF 同协议结果不是其最优部署性能。

保留 20/20A、101/101X、车身编号和站牌反例，同时回归原始 912 连续录像。速度与准确性一起报告，不放宽证据过期限制来制造通过结果。

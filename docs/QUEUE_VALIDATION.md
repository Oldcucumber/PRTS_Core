# 叫号识别与连续交互

当前采用 OCR 实际字串、可见字符间距和相邻栏目关联。用户等待号码只进入最后的完整标识匹配，不用于切分长数字或补写模型答案。C-002 保留为 C002；窗口、等待栏、价格与已叫号码分别处理。

## 首次验证与修正回归

| 阶段 | 输入 | 确认正目标 | 指定负目标误确认 |
|---|---|---:|---:|
| 首次 v1 | 3 张真实照片 | 0 / 17 | 0 / 15 |
| v1 修正回归 | 同一批已用于调整的照片 | 17 / 17 | 0 / 15 |
| 首次 v2 | 5 张新照片，推理前冻结标签 | 1 / 8 | 2 / 32 |
| v2 修正回归 | 同一批已用于调整的照片 | 4 / 8 | 0 / 32 |

目标数不是独立照片数：餐厅一张图有 16 个号码。新医院、银行照片与 v1 银行屏同属 Vorsea 来源，不能据此声称充分跨供应商泛化。另三张来自不同来源的数码屏/广告：价格反例未误确认，但两个 LED 屏的栏目语义仍未解决。

`first-pass-v1/`、`first-pass-v2/` 保留首次失败，后续 `layout-dev-*` 均为开发回归。v2 最初把“Loket 1 / 2”关联到上方的大叫号标题，因此误报窗口号；修正后带标签的窗口字段保持自己的角色，窗口下方的独立票号另行判断。

剩余 LED 场景中，OCR 已读到 555、398、554 和 43，系统仍未确认它们属于已叫号码。上下文重读还产生“398-5 / 554-6”这类票号与柜台混合行；明确的数字连字符/斜杠组合不产生确认或候选，字母前缀 C-002 不受影响。

## 已接入的处理

1. 有界 OCR 后，根据数字行自身四角位置，最多重读四个局部上下文，不使用人工叫号屏框。
2. 对粘连纯数字做透视校正和像素间距检查。仅在可见字形数与实际 OCR 字数一致时按明显间距分组；不假定固定三位，也不按等待目标切分。
3. 在文字行基线坐标中关联相邻标题，处理相机倾斜。窗口、价格、等待行不会继承旁边的叫号角色。
4. 完整票号和已叫栏目同时成立才提醒。未确认栏目时保留候选；取消、替换和去重继续适用。
5. 广播提取服务对象，排除“到 3 号窗口”的目的地数字、否定和询问。ASR 丢失的字母不根据目标回填。

## 连续输入与输出

`queue-montage-input-v1/` 将银行、餐厅、医院三张真实照片拼接成 48 秒输入，包含四段 Microsoft Huihui 合成语音及标明的 B003 / 取消文字命令。它验证真实 OCR、连续 PCM、任务修改/取消和运行时 TTS，不代表真实排队过程录像或现场 ASR 精度。

`queue-dml-v1/` 实际处理 96 / 96 帧，窗口 3 未误报，确认 215、494 和 B003，证据年龄约 0.859、0.578、0.500 秒，无记录到的工作线程错误。回放暴露分句问题：“改为等二百一十五号，叫到时提醒我”分成两句后，尾句重复索要目标。已增加明确提醒尾句的延续动作，保留任务开始时间、版本和已提醒状态，不重启等待；后续实跑另行记录。

## 便携实现与未采用方案

数字间距拆分已实现为纯 C++ `prts_queue_split_rgb`，Windows 实编译，11 组固定输入与 Python 分组一致、四角误差低于 1 像素。Swift `QueueReader` 接入局部 OCR、该 C ABI 和字段/广播规则，保留 Vision 观测四角。22 个 Swift 文件通过语法树检查；另准备 14 个广播字段及 8 个实际 OCR 布局的 Foundation 对照。**未执行 Swift 编译、Apple OCR 或 iPhone 验证**。

整图读数字、检测器裁屏、按 OCR 行编号输出 JSON、黄色框字段分类均保留失败。字段分类模型把广告价格、票号/柜台混合行也判成叫号，未接入生产提醒。见 `semantic-probe-v1/`、`display-probe-v1/`、`text-role-probe-v1/`、`field-role-probe-v1/`。真实广播 A108 的字母丢失仍未解决。

## 首次 v1 详细记录（修正前）

`tests/fixtures/queue_holdout_v1.json` 在推理前冻结三个公开照片及人工标签，原图、作者、许可和 SHA256 在 `outputs/stage2/queue-holdout/data/`。输入是静态照片，不是到号变化视频或真实广播。

`first-pass-v1/` 使用当前生产 PP-OCRv6 small 与 Tasks，**17 个预期号码全部未触发提醒，15 个指定干扰请求没有误报**。首轮结果及代码快照保留，后续修正不能覆盖为“独立通过”。

香港餐厅图中，右屏八个数字被 OCR 分开读出，但“取餐號碼”误读，英文 PICK-UP NUMBER 未进入中文屏幕语义条件；左屏两行各四个号码被 OCR 拼成连续长数字。不能用待等号码反向切分这串数字来制造正确匹配。

银行屏显示 C-002，当前完整标识规则不能把字母与连接符后的数字作为同一号码；屏幕还包含柜台 3、汇率和利率。修正时必须保留字母/前导零，区分叫号、柜台和广告数字，不能仅添加一种界面上的词就宣布泛化通过。第三张邮局广角照片 LED 模糊，未标正例，仅测明确不存在的号码。

下一步将使用目标无关的屏幕语义解析和区域关联，结合 OCR 实际字串核验；与公交一样，单一模型推测只形成候选。真实广播中 A108 的字母丢失仍需独立解决，不能用等待目标去补写 ASR。

`semantic-probe-v1/` 的目标无关 VLM 候选能读出银行 C-002，但餐厅整图数字大量错误且输出不是有效 JSON，邮局模糊图还生成了不存在的数字串。该候选没有接入生产提醒，原始输出保留；不能以单模型自由回答替代叫号证据。

后续比较先利用现有检测器的显示屏框，把屏幕从大场景中裁出后再识别，避免整图缩小造成标题和号码粘连；每个屏幕独立关联当前叫号、等待列表与柜台字段。该思路尚未实现或验证，不能改变上述首轮结果。

`display-probe-v1/` 首次自动框选也失败：YOLO11n 在餐厅图选中了店铺招牌，未框住两块真实叫号屏；银行框正确，但简化数字提示词的 VLM 输出发生重复扩展。未接入提醒。需要改进屏幕区域提议与号码字段关联，不能用人工选框把这次失败改写为成功。
